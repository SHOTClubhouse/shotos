# learning-loop

**Turn an event into an improvement in six steps, and make a lesson a rule only when it has earned it.**

The agent follows observe, diagnose, propose, test, promote, check. It records facts first, lists causes with the ones ruled out, proposes one small change, and tests it against a case that would have caught the original event and a contrary case where the new rule would be wrong. A rule needs evidence, a test, a contrary case, the authority that approved it, a review date and what it supersedes.

It supports Sustain and Scale. It serves rule 2, Agree acceptance first, rule 3, Read back the real result, and rule 4, Claim only what you can show.

## The problem it solves

At a fictional firm, Northgate Cycles, an agent once quoted a workshop price from an old list. Someone added a rule: "Always check the price list date." Later, someone added another about invoices after a different slip. A year on, the instructions hold forty rules, some contradicting each other, none with a reason, and the agent hedges everything.

With the loop, the price slip becomes one record: the observed events, the cause (two price lists in the shared folder), one small change (read the list marked current), the test that would have caught it, a contrary case (a quote for last year's price on request), the owner who agreed and a review date in three months.

## When to use it, and when not to

Use it after a rejected output, an incident, a retrospective, or repeated edits to the same kind of output, and before adding any rule. Skip it for a one-off slip with an obvious local fix.

## Who it is for

- **Engineering or practice lead:** a way to improve instructions without bloat.
- **Product owner or analyst:** keeps each rule tied to evidence.
- **Small team lead:** a simple form to capture lessons.
- **Governance or risk owner:** every rule has an approving person and a review date.

## How to use it

Ask:

> Three of the last twelve price quotes used an out-of-date list. Run the learning loop on it. Propose one change and write the test and the contrary case. I own the quoting instructions and will decide.

You get a lesson record on [template.md](template.md). Read the contrary case first; if it is weak, send the proposal back.

## Needs

Nothing beyond the agent.

## Tips and common mistakes

- Write the contrary case before you write the rule.
- Rule out causes. "The model slipped" is the easy answer and often the wrong one.
- One change per record.
- The owner promotes, not the agent.
- Put the review date where someone will see it.

## Limits

- Small samples give weak evidence. The record shows how strong it is rather than hiding it.
- The loop adds work. Use it for repeated problems and keep one-offs quick.
