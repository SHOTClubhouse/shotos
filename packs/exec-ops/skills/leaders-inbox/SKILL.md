# Leader's inbox

Take unstructured input and give back a short list of recommendations, each routed to one place. The leader thinks quickly and loosely; the skill's job is to keep the meaning and drop the noise, and to refuse to invent a task from a half-thought.

Stage: Scope. Rules: 2 Agree acceptance first, 4 Claim only what you can show.

## Context and handoff

Check the leader’s current priorities, deadlines, delegated owners and existing decisions before creating an action.

Use `decision-brief` when a decision needs options. Update the existing task or decision log rather than duplicating it.

## Start here

**Minimum to start:** the pasted batch and the leader's current priorities. If priorities are unknown, route anyway and mark each task "needs detail". **First output:** the recommendations table, one row per item, before any reasoning. **Uncertain:** unverified items stay labelled hypothesis or target, and unmatched records are "no match found in the sources checked". **Handoff:** list the decisions only the leader can make first, each with the question and who decides.

## When not to use this

Skip it for a single, already-clear task (just do it or file it), for a finished decision that only needs recording, or when the leader wants a brainstorm rather than routing.

## Steps

1. **Split the input into items.** One idea, link or note per item. Keep the original wording and note its source (a pasted note, a link, a voice dictation, a forwarded message).
2. **Reduce each item to meaning.** Write one sentence for what it means for the work, then label each statement: **fact** (checked or sourced), **hypothesis** (a belief to test) or **target** (something wanted). Never present a hypothesis or target as fact.
3. **Match against existing records.** Search the leader's task list, decision log and project notes for the same thing. If a match exists, update that record or link to it; do not create a duplicate.
4. **Route to exactly one outcome.**
   - **Decision:** a choice only the leader can make. State the question and who decides. Hand to `decision-brief` if it needs preparing.
   - **Task:** work with a clear home. Put it in the owning project with owner, scope, evidence of done and dependencies. If any of those is unknown, mark it "needs detail" rather than guessing.
   - **Shared context:** background others need to see; add it to the project's notes.
   - **Long-term memory:** only when the leader explicitly says to remember it. Otherwise never write to memory.
   - **No record:** if the item is a passing thought, say "no record yet" and leave it. Nothing is forced into a record. Say plainly which notes are not really tasks (a preference, a half-idea) and so do not need a record. If the leader has asked for a record of every note, make what was asked, mark the ones that are not tasks as notes or "needs detail", and say that you did.
5. **Lead with recommendations.** Put the recommendations table first, then the detail. Keep reasoning short.
6. **Read back.** After any record is created or updated, open it and confirm it says what the table says. Report items that could not be filed and why.
7. **Stop at the boundary.** Do not message anyone, assign work to a person, or change another team's project without the leader's yes. A request that names the person ("assign it to Aisha") is that yes for a record inside the project; telling Aisha is not. Propose; do not do.

## Output

Use [template.md](template.md): recommendations first, then one row per item with source, meaning, label, match and route.

## Checks

- Every item has exactly one route, or "no record yet".
- Facts, hypotheses and targets are labelled separately.
- Duplicates were checked for before any new record.
- Each task has owner, scope, evidence of done and dependencies, or says what is missing.
- Nothing went to long-term memory without an explicit request.
- Notes that are not tasks are named as such and are not dressed up as tasks.
