# Task data access card

Use this before a task reads a connected system or moves information between tools. Link it from the existing work record. Keep the source data in its approved system.

- **Task and purpose**
- **Data owner and approval reference**
- **Approved account, assistant or runtime**
- **Output location and permitted readers**
- **Review date or end of access**

| Source and classification under team policy | Allowed scope and fields | Allowed operation | Destination or access limit | Status and approval evidence |
| --- | --- | --- | --- | --- |
| | | | | |

**Before the first read**

Check the account and approved scope. Use the smallest approved sample to prove access. Leave access pending if the owner or allowed use is unclear. Record evidence references here without copying source rows, credentials or private message text.

**When the scope changes**

Update the card for the new purpose, source, fields, audience or destination. Route the change to the data owner before widening access.

## Fictional example

A service lead wants a weekly count of open jobs by site. The data owner approves reading the shared operations export using the team's approved assistant.

| Source and class | Allowed scope and fields | Allowed operation | Destination or access limit | Status |
| --- | --- | --- | --- | --- |
| Weekly operations export, internal | Named export for the agreed week. Site code and job status only. | Read and aggregate. | Aggregate count in the operations review folder. | Approved in the task record. |
| Linked job notes, restricted under the team's policy | Outside the approved export. | Leave unopened. | Keep in the service system. | Outside this task. |
| Supplier mailing list, confidential | A request to send the counts to suppliers arrives later. | Hold pending a separate owner decision. | No external destination approved. | Pending. |

A connected account may show all three sources. The first row covers the task. The others remain outside the approved scope.
