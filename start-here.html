Start here

SHOTos turns the AI assistant you already use into a small, careful team: one that starts from your context, agrees what done looks like before it starts, checks its own work where it lives and tells you plainly what it could not check. It is free and open source. Reading this page takes about ten minutes. Setting up takes about five.

Why it exists

Most AI help fails in the same few ways. The assistant guesses at facts it was never given. It does the task it imagined rather than the one you meant. It says "done" from memory of what it intended, not from looking at the result. And it writes an invented number with the same confidence as a real one.

None of that is fixed by a cleverer prompt. It is fixed by a process: say who the work is for and what would show it worked, test the idea small, check the real result, and hand it to someone who can own it. Good teams already work this way. SHOTos writes that process down so an agent can follow it and a person can check it did.

How it works

Three things hold SHOTos together.

Four rules inside every task. Stop at the boundaries, so nothing is sent, spent, published or deleted without your yes. Agree acceptance first. Read back the real result. Claim only what you can show. The rules live in one short file, the working agreement. A project install loads it in every session. In a chat app, add it to the project instructions or attach it to the chat.

Six stages for work that matters. Scope, Hypothesise, Operate, Track, Own, and Sustain and Scale. Small jobs use one stage. A change that someone will rely on moves through all six, and each stage ends with a decision a person makes. The six stages in detail

One brief, read first. You describe your organisation, your people, your limits and the numbers you rely on once. Wherever the working agreement is loaded, every skill reads the brief before it asks you anything. See the next section.

Write one brief

Copy the brief template, fill it in and save it as BRIEF.md in your project folder, or add it to your chat project. Rough answers are fine and blank lines are fine. The agent asks only for what changes its result, and writes "not known" or "not measured" where a gap remains.

Two parts of the brief do most of the work:

  • The limits. Write down what the agent must never do without asking, and what data it must never copy. The working agreement already stops it sending, publishing, spending and deleting without a yes. Your limits add the rules that are particular to you.
  • Numbers we rely on. Give each number a source and the date you read it. A number without a source stays marked [unverified] in anything the agent writes, so a guess never turns into a headline.

The brief is context, not permission. It can add limits but never removes one. When a fact in the brief disagrees with the task in front of you, the agent uses the task and tells you which line is out of date. When a limit disagrees, it applies the stricter one and asks you.

Keep private material out of it. Personal details, health information, passwords and customer records belong in their own systems. You can say where they live; the agent opens them only for a task that has approval for that data.

Set up in five minutes

The same skills work in three ways. Pick the one that matches how you work today.

A. One skill in your chat app. Best for trying SHOTos on one real task.

  1. Download a skill ZIP from the latest release. Capture the Problem is a good first one.
  2. Upload it as a skill. In Claude, open Customize → Skills and upload the ZIP without unzipping it. In ChatGPT, use Skills → Create → Upload from your computer where your workspace allows it. Step-by-step guide
  3. Start a fresh chat and attach your BRIEF.md and the working agreement. A single skill does not carry either, so ask the agent to read both first, then ask for the skill by name.

B. A chat project. Best for a team that works in Claude or ChatGPT every day.

  1. Create a project and paste the working agreement into its instructions.
  2. Add your BRIEF.md and the skill files you use most to the project's files.
  3. Ask for a skill by name in any chat inside the project. Step-by-step guide

C. A terminal. Best if you already use Claude Code, Codex or another coding agent.

  1. From the folder that holds your project, clone SHOTos beside it, move into your project and run the installer. Preview first with --dry-run. Replace my-project with your project's folder name.

    git clone https://github.com/SHOTClubhouse/shotos.git
cd my-project
python ../shotos/install.py --runtime claude --scope project --dry-run
python ../shotos/install.py --runtime claude --scope project

    Use --runtime agents for Codex and other agents, and add --pack <name> for each pack you want.

  2. Copy the brief template into place and fill it in: cp .shotos/templates/brief.md BRIEF.md

  3. Open a fresh session in the project and ask for a skill by name. Step-by-step guide

Whichever route you choose, check the first result before relying on it. The skill's README says what a good result looks like.

The twelve steps

These twelve core skills take one piece of work from a rough idea to something a team owns. They are grouped by the stage where this route uses them; a skill's own README lists every stage it serves. Each skill says when to hand off to a related one. You do not have to run all twelve: start at the step that matches where your work is today.

The example below each step follows Northbank Community Football, an invented club that wants more families at its Saturday sessions. Northbank and its numbers are illustrative, not real.

Start, then Scope: agree what the problem is

1. Route the Work. Usable in any stage, and run first here. Writes one line saying what the work is, who it is for, how risky it is and who checks it. Northbank: "Asset: open-day plan. Reader: the committee. Risk: medium, because the registration list holds children's details, so the agent works from counts only. Proof: the chair approves the plan."

2. Capture the Problem. Turns rough notes into a problem statement that separates what people saw from what they want built. Northbank: "Parents say they did not know sessions existed. Nobody has counted how many new families came this season: not measured."

3. Baseline. Records how things are today, with a source and date for every number. Northbank: "New families this season: 6, a count the membership secretary gave from the registration list on 3 October. Website visits to the sessions page: not measured."

Hypothesise: make a small, testable bet

4. Hypothesis Card. Writes the bet down: we believe this change will cause this result, and we will know because this number moves. Northbank: "We believe an open day promoted through the local primary school will bring at least 10 new families, measured by registrations in the four weeks after."

5. Agree Acceptance. Agrees the owner, the checks and at least one case that should fail, before any work starts. Northbank: "The flyer must show the correct date, time and price. A flyer with a child's photo and no consent fails."

6. Experiment Plan. Plans the smallest test that would prove the bet right or wrong, with a stop rule. Northbank: "One open day, one school, one flyer. Stop if fewer than 3 families register."

Operate: do the work, small first

7. Pilot Before Scale. Tries a few varied items before any bulk or live change. Northbank: "Draft the flyer for one class and test the booking link on a phone. The head teacher approves the flyer before it goes to any parent, and the whole school waits for that first result."

8. Label the Proof. Marks every figure as literal, inferred or illustrative, so nobody mistakes an example for a result. Northbank: "'30 children attended, 18 of them under 9' is literal, a count by age group that the session lead reported. 'The school flyer reached the younger age groups best' is inferred from that split."

Track: compare the result with the baseline

Report with Evidence also serves Operate, whenever a step needs an honest report.

9. Report with Evidence. Reports what happened with a Claims block that separates what was checked from what was not. Northbank: "11 new families registered in the four weeks after the open day, a count from the membership secretary. Whether the flyer caused it: not tested."

10. Evidence Pack. Puts the baseline, the result and the gaps side by side so the owner can decide: keep going, change course or stop. Northbank: "11 new families against a target of 10, so the target was met. Retention after the first month is not yet known."

Own: hand it to the people who will run it

11. Evidence Handoff. Hands the work to its new owner with what was agreed, what was proved and what is still open. Northbank: "The membership secretary takes over the open day for next season, with the checklist, the flyer source and the two open questions."

Sustain and Scale: keep it working, then grow it

12. Learning Loop. Looks at what happened, tests one improvement and changes the method only when the test supports it. Northbank: "Next season, test a second school. Keep the first school's process unchanged so the two results can be compared."

Every core skill sits in one of these stages. The skill catalogue lists all of them, and what you can do sorts them by the job you have in front of you.

Questions people ask

Does it cost anything? SHOTos is free. You use the AI assistant you already have, on whatever plan you already pay for. Some routes, such as skills in a chat app or a coding agent, depend on what your plan and workspace allow.

Which assistants does it work with? Claude, ChatGPT, Claude Code, Codex, Gemini CLI and other agents that read an instructions file. The runtime guide covers each one.

Do I need all of it? No. Start with one skill on one real task. Add the working agreement when you want the four rules in every session, and the brief when you are tired of explaining yourself.

Is my data safe? The skills and templates are text files and send nothing anywhere by themselves. The optional automations pack runs in your own Google account, and its README says what it connects to. Your data goes wherever your assistant sends it, so check your plan's data settings, keep private records out of the brief and the prompts, and use the trust pack before anything is shared.

What if the agent gets something wrong? It will, sometimes. That is why every skill reads back the real result and marks what it could not check. Check those marks first. Only a person can accept the work.

Is this legal, financial or professional advice? No. Treat anything in those areas as a draft for a qualified person to check.

Can I share it or change it? Yes. The documentation, skills and templates are under CC BY 4.0 and the code is under the MIT licence. Give credit and say what you changed.

Do this tonight

Fill in the brief, then give one real, messy note to Capture the Problem: a complaint, a request or an idea someone keeps raising. It takes about ten minutes. You will have a problem statement that says what is known, what is not, and the cheapest way to find out.
